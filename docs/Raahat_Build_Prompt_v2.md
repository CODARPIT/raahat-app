# Build prompt v2: Raahat (राहत) — disaster photo triage with Cloudinary AI

You are a senior full-stack engineer. Build a complete, working, deployable web app called **Raahat** for a hackathon (Hacktober HackDays 2026, "Tech for Social Good"; the project **must** use the Cloudinary tech stack).

Work in **priority tiers** (§2). Finish and verify each tier before starting the next. Keep `npm test` and `npm run build` passing at every step. A small, reliable app beats a big, fragile one — **the live demo must not fail on stage.**

---

## 1. Problem and solution

**Problem.** During floods, earthquakes, cyclones and landslides in India, control rooms receive hundreds of citizen photos, mostly **forwarded on WhatsApp**. They arrive with no priority, many duplicates, old or fake images, **usually no location** (WhatsApp strips EXIF GPS), visible faces of victims, and over weak internet. Coordinators waste critical time sorting instead of dispatching.

**Solution.** Raahat turns that stream into a ranked, de-duplicated, privacy-safe queue on a live map:

1. Citizens report through **WhatsApp** (send a photo, then a location pin) or a simple **web page**, in Hindi or English.
2. **Cloudinary AI Vision** classifies the hazard, counts people, estimates water depth, flags screenshots/memes, and summarises in English and Hindi.
3. A **perceptual hash** merges forwarded copies; different photos of the same incident corroborate it.
4. A **transparent, explainable score** ranks reports. Nothing is deleted; doubtful reports go to human review.
5. Reports **without a location are never dropped**: the coordinator pins them on the map, helped by place names from the note.
6. Faces are pixelated on every public image; public locations are rounded.
7. Responders get a ranked queue + map, a 2G mode, and a one-click **WhatsApp alert card** generated by a Cloudinary URL.

Floods are the lead example; it must work for any disaster that can be photographed.

## 6. Data model

One report = one Cloudinary asset in `raahat/reports`, tagged `raahat_report`.

```ts
type Category = "trapped_or_injured" | "fire" | "structural_collapse" | "landslide"
  | "electrical_hazard" | "flood" | "road_blocked" | "relief_needed" | "waterlogging" | "no_emergency";
type Severity = "critical" | "high" | "moderate" | "low";
type Status = "new" | "verified" | "dispatched" | "resolved" | "rejected";
type WaterDepth = "none" | "ankle" | "knee" | "waist" | "chest_or_more" | "unknown";
type LocationSource = "gps" | "map_pin" | "whatsapp_pin" | "exif" | "coordinator" | "missing";
type Channel = "web" | "whatsapp";

interface ScoreBreakdown { label: string; points: number }[]

interface Report {
  publicId: string; resourceType: "image" | "video"; createdAt: string; channel: Channel;
  lat: number | null; lng: number | null; locationSource: LocationSource; placeHint: string;
  note: string; lang: "en" | "hi";
  categories: Category[]; primaryCategory: Category; severity: Severity; score: number;
  breakdown: ScoreBreakdown[];
  peopleVisible: number; peopleInDanger: boolean; waterDepth: WaterDepth; accessBlocked: boolean;
  summary: string; summaryHi: string; status: Status;
  needsReview: boolean; reviewReasons: string[];   // e.g. "looks like a screenshot", "matches an older photo"
  duplicateOf: string | null; corroborations: number;
  originalBytes: number; thumbBytes: number; aiMode: "live" | "demo"; phash: string | null;
  reporterHash: string | null;                      // sha256 of WhatsApp number, never the raw number
}
```

Store fields as short context keys; mirror key fields as tags (`sev_*`, `cat_*`, `status_*`, `needs_review`, `duplicate`, `no_location`, `ch_whatsapp`) so the Media Library is a fallback console. Store the breakdown as compact JSON (keep context values under Cloudinary's size limits).

## 7. Triage pipeline (shared by web and WhatsApp)

`triage(input)` where input = `{ publicId, resourceType, lat?, lng?, locationSource, note, lang, channel, reporterHash? }`:

1. **Fetch asset** via Admin API with `phash: true` and `image_metadata: true`.
   - If no lat/lng was given and EXIF GPS exists, use it (`locationSource: "exif"`).
2. **AI analysis** (parallel, each wrapped in `RAAHAT_AI_TIMEOUT_MS` via `AbortController`) on derivative `e_improve:outdoor/c_limit,w_1024/q_auto:good`:
   - `POST https://api.cloudinary.com/v2/analysis/{cloud}/analyze/ai_vision_tagging` — one plain-English definition per category (max 10). Read `data.analysis.tags[].name`.
   - `POST .../analyze/ai_vision_general` — one prompt demanding **only JSON**: `is_real_photo, is_disaster_related, people_visible, people_in_danger, water_depth, access_blocked, summary (≤25 words), summary_hi (Devanagari), place_names (array of place/landmark names visible in signs or text)`. Read `data.analysis.responses[0].value`.
   - Extract the first `{...}`, parse, **sanitise every field**. Malformed replies must not crash triage.
   - Read `limits.addons_quota[0].remaining` from responses and keep the latest value in memory for the control room.
3. **Fallback**: `demo` mode, or `auto` on error/timeout → rule-based reader of the note (English + Hindi keyword regexes). Mark `aiMode: "demo"`; UI label **"rule-based"**.
4. **Place hint**: combine place names from the note (simple pattern: words after "near / opposite / behind / पास / सामने" plus capitalised tokens) and from `place_names`. If location is missing, optionally geocode the hint with Nominatim (bounded to India, cached) and show it as a **suggested** pin — never auto-confirm it.
5. **Score + breakdown, duplicates, corroboration** (§9). Reports with no location can still be duplicates (phash only) but cannot corroborate.
6. **Measure thumbnail bytes** (fetch once; also warms the CDN).
7. **Save** to Cloudinary **and** put the full report in the in-memory cache. Re-score and save primaries it duplicates or corroborates.

### Routes
- `POST /api/sign` — sign Upload Widget params only for folder `raahat/reports` + tag `raahat_report`.
- `POST /api/reports` — web intake → `triage`. Location optional; if absent, `locationSource: "missing"`.
- `GET /api/reports` — merged list (§8). Responders get everything; public view drops notes, phash and reporterHash, rounds lat/lng to 3 decimals, hides `needsReview`, `rejected` and unlocated reports.
- `PATCH /api/reports` — responders only: `{ publicId, status }` or `{ publicId, lat, lng }` (coordinator pin → `locationSource: "coordinator"`, then re-run corroboration).
- `POST /api/responder` / `DELETE` — passcode → httpOnly SameSite=Lax cookie with `sha256("raahat:"+passcode)`, 12 h.
- `GET /api/health` — Cloudinary reachable, AI mode, last known AI quota, cache size. Use it before going on stage.

## 8. Consistency and rate limits ("Cloudinary as database" safely)

- Keep a **module-level in-memory cache** (`Map<publicId, Report>`) of reports written or updated by this server instance.
- `listReports()` = Search API results **merged with** the cache by `publicId`, preferring the newer copy. A just-triaged report therefore appears instantly even before Search indexes it.
- **Duplicate matching uses the merged list**, so the "forward the same photo twice" demo works seconds apart.
- Cache Search results for 10 s; on HTTP 420/429 from Cloudinary, retry once with backoff, then serve the cached list with a "data may be a few seconds old" note instead of an error.
- Document honestly: on serverless, instances don't share memory, so a production version would add Redis or a database; the cache exists for consistency on a single instance and for demo reliability. For the live demo, warm the app and run it on one instance (or `npm start` locally as a backup).

## 9. Scoring, explainability and fake-photo checks (`src/lib/triage.ts`, unit-tested)

```
Weights follow one rule: threat to life first, then how fast the hazard spreads or escalates,
then how much it blocks access to help.
trapped_or_injured 40 (life at risk now) · fire 35 (spreads in minutes) ·
structural_collapse 30, landslide 30 (can trap people, may recur) ·
electrical_hazard 25 (lethal near water) · flood 20 (rising, wide area) ·
road_blocked 15, relief_needed 15 (blocks help / basic needs) · waterlogging 10 · no_emergency 0

score = weight(primary)
      + 0.25 × sum(other category weights)
      + 30 if peopleInDanger
      + 1.5 × min(peopleVisible, 10)
      + depth: ankle 2, knee 8, waist 15, chest_or_more 22
      + 5 if accessBlocked
      + 4 × min(corroborations, 5)
needsReview → score × 0.3
primary == no_emergency → score ≤ 15
clamp 0–100; severity: critical ≥ 70, high ≥ 45, moderate ≥ 25, else low
```

- `scoreReport()` returns a **breakdown** list (e.g. `People trapped +40`, `Someone in danger +30`, `Waist-deep water +15`, `2 other reports +8`, `Looks like a screenshot ×0.3`). Show it in the detail panel under **"Why this score"**. Put the weight rationale in a code comment and the README, and state that weights are meant to be tuned with a real control room.
- **Duplicate**: phash Hamming ≤ 10/64 and (within 2 km, or either report has no location) → merge into the oldest primary.
- **Corroboration**: same primary category, both located, ≤ 300 m, ≤ 12 h.
- **Fake / old-photo checks — be honest about coverage:**
  - AI flags screenshots, memes, drawings, AI-looking images, photos of screens → `reviewReasons`.
  - If EXIF `DateTimeOriginal` exists and is older than 7 days → "photo taken on <date>".
  - Keep a small **known-old-photos** library (`raahat/known_old`, tagged `raahat_known_old`, seeded with photos from past disasters). phash match → "matches an older photo from <caption>". This catches famous recycled images, not every old photo; say so in the README.

## 10. WhatsApp intake (P1, Twilio Sandbox)

`POST /api/whatsapp` (Twilio webhook, `application/x-www-form-urlencoded`):

1. **Validate `X-Twilio-Signature`** with `twilio.validateRequest(authToken, signature, PUBLIC_BASE_URL + "/api/whatsapp", params)`. Reject if invalid.
2. `reporterHash = sha256(From)`. Never store the raw phone number.
3. **Photo message** (`NumMedia ≥ 1`, `MediaUrl0`, `MediaContentType0`, caption in `Body`):
   - Upload to Cloudinary from the media URL. Twilio media URLs need HTTP Basic auth: fetch the bytes server-side with `TWILIO_ACCOUNT_SID:TWILIO_AUTH_TOKEN`, then upload the buffer (`upload_stream`) to `raahat/reports` with tag `raahat_report`.
   - Run `triage` with `locationSource: "missing"`, `channel: "whatsapp"`, note = caption.
   - Remember `reporterHash → publicId` as "awaiting location" (in memory and as a context key, 30 min).
   - Reply (TwiML `<Response><Message>`), in Hindi if the caption is Hindi: "Report received. Priority: HIGH. Please share your location pin (📎 → Location) so responders can find you. If life is in danger, call 112."
4. **Location message** (`Latitude`, `Longitude`, optional `Address`/`Label`): attach it to that reporter's awaiting report (`locationSource: "whatsapp_pin"`), re-run matching, reply "Location added. Responders can see your report."
5. **Text only**: reply with how to report (send a photo, then a location pin).
6. Must respond within Twilio's timeout: if triage is slow, reply immediately with "Received, analysing…" and finish triage in the same request only if it fits; otherwise rely on the AI timeout + fallback.
7. Landing page shows the sandbox number and join code with clear steps.

## 15. Prepared answers (put in README "FAQ")

- **"Citizens won't open a website mid-flood."** → They don't have to: WhatsApp intake; the web page is for volunteers and responders.
- **"Forwarded photos have no location."** → Never dropped: we ask for a location pin on WhatsApp, use EXIF if present, extract place names, and the coordinator pins it on the map.
- **"Isn't Cloudinary-as-database fragile?"** → Cloudinary is the system of record; an in-memory cache gives read-your-writes and shields rate limits; production adds Redis/Postgres.
- **"AI Vision quota/latency?"** → Timeout + rule-based fallback, honestly labelled; quota shown in the control room.
- **"Does it detect old photos?"** → It catches screenshots/memes, EXIF dates, and famous recycled photos in a known-old library; not every old photo — said plainly.
- **"Why is fire 35 and trapped 40?"** → Life-threat first, then spread risk, then access; every point is shown in "Why this score" and tuned with a coordinator.
